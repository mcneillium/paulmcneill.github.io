# Performance review

**Tooling caveat**: Lighthouse / Pagespeed / WebPageTest aren't running
in this environment. The review below is **structural** — based on what
the site does and doesn't do — not measured.

## Structural assessment

### What's working

- **One CSS file**, hand-written, ~41 KB unminified. No Tailwind, no
  PostCSS, no SCSS at runtime.
- **One JS file**, ~5 KB, defer-loaded. No frameworks, no jQuery, no
  React.
- **No third-party scripts at runtime** — Google Fonts is the only
  external CSS, and it's `preconnect`ed.
- **All images** are served via `<picture>` with a WebP source +
  original fallback. Generated by `scripts/optimize-images.js`.
- **Below-fold images** use `loading="lazy"` and `decoding="async"`.
- **Above-fold post hero** uses `loading="eager"` + `fetchpriority="high"`.
- **GitHub contribution graph** is data-`src` lazy — fetched only when
  the section enters the viewport.
- **YouTube embeds** use a lite-embed pattern: thumbnail loads first,
  iframe is only created on click.
- **Fonts** use `&display=swap` (set by Google Fonts CSS).
- **Mobile menu lock-scroll** sets `overflow: hidden` on body, not on
  `html`, avoiding scroll-jank on iOS Safari.

### What's deliberately **not** doing

- **No service worker.** Stale-cache bugs aren't worth the offline
  story for a content-light static site.
- **No code-splitting.** The single JS bundle is small enough.
- **No HTTP/2 push, no resource hints beyond `preconnect`.** Pages
  controls the headers; we don't get to add `Link: ; rel=preload`.
- **No prefetching of project pages.** Could be worth it later if
  visitor flow shows a clear "home → project" pattern.

### Likely Lighthouse losses (without measurement)

- **Largest Contentful Paint** could be the hero `h1` plus its custom
  font load. The hero has no image LCP candidate; the title using
  Instrument Serif (display: swap) means a brief FOUT, which can
  delay LCP. Mitigation: rely on the swap fallback and don't
  preload fonts (currently not preloaded).
- **Cumulative Layout Shift**: marquee starts animating immediately;
  reveal elements move 32px on first paint. The reveal entries set
  `opacity: 0` initially so the shift is visual but doesn't move
  later content unexpectedly. Should be ~0.
- **Total Blocking Time**: should be near-zero — the JS is small,
  defer-loaded, and uses `requestAnimationFrame` for scroll work.

## Things to do before claiming "fast"

1. Run Lighthouse against the live URL (mobile and desktop).
2. Run WebPageTest on a slow 3G connection — that's the test that
   matters for "first impression on a phone".
3. Capture LCP / CLS / TBT in `docs/performance-review.md` so future
   changes can compare against a baseline.

## Things to consider only if measurement says so

- Self-hosting Google Fonts to remove the cross-origin request.
- Inlining critical CSS for the nav + hero (currently the full sheet
  is render-blocking).
- Switching the marquee to `prefers-reduced-data` to skip on metered
  connections.
- Preloading the cover image on case study pages.

None of these are worth doing speculatively. Do them when a measured
metric demands them.

## Repo size

- Repo: 36 MB on disk (including generated WebP siblings).
- Site (`_site/`): ~50 MB built (most is gallery thumbnails).

This is fine for GitHub Pages. If repo size becomes a problem, the
unused legacy images in `docs/missing-assets.md` are the first cut.
